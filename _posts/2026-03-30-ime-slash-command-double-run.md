## 증상

위키 에디터에서 `/페이지 생성` 을 **한글로 직접 타이핑하고 Enter** 를 누르면, 새 페이지가 1개가 아니라 **2개** 생겼습니다. 쓸데없는 빈 페이지가 쌓이니 사용자 입장에서는 데이터가 꼬인 것처럼 보이는 문제였습니다.

## 관측 사실

- 네트워크 탭을 보면 페이지 생성 API 가 프론트엔드에서 **두 번** 호출됐습니다.
- 백엔드는 요청 두 개를 받아 정상적으로 두 개를 만들었을 뿐이었습니다. 문제는 "왜 프론트가 두 번 부르나"였습니다.
- 다른 슬래시 명령(제목, 목록, 토글 등)은 겉보기에 정상이었습니다.

## 배경: IME 조합 중의 Enter

한글처럼 조합형 입력기(IME)를 쓰는 언어는, 마지막 글자를 아직 조합 중인 상태에서 Enter 가 들어오면 keydown 이벤트에 `isComposing = true` 가 붙습니다. 이때 바로 명령을 실행하면 조합 중인 글자가 깨지거나 이상하게 동작하기 때문에, 보통은 **조합이 끝나는 `compositionend` 시점으로 실행을 미룹니다.**

## 원인: 같은 문제를 두 곳에서 풀고 있었다

코드를 따라가 보니, 이 "실행 미루기"가 **서로 다른 레이어에 두 번** 구현돼 있었습니다.

**경로 A — 명령 레이어**

```ts
// 모든 슬래시 명령을 감싸는 래퍼
function safeCommand(run) {
  return (...args) => {
    if (isComposing) {            // 조합 중이면
      pendingCommand = () => run(...args);   // 보류해 두고
      return;
    }
    run(...args);
  };
}
// 전역 compositionend 리스너가 pendingCommand 를 실행
```

**경로 B — 메뉴 UI 레이어**

```ts
// 캡처 단계 keydown: 조합 중 Enter 면 표시만 해 둔다
if (e.isComposing && e.key === 'Enter') {
  e.preventDefault(); e.stopPropagation();
  pendingEnter = true;
}
// compositionend: 선택된 메뉴 항목을 '클릭'해 준다
if (pendingEnter) setTimeout(() => selectedItem.click());
```

`compositionend` 가 한 번 발생하면:

1. 경로 A 가 보류해 둔 명령을 실행합니다. → API 1회
2. 경로 B 가 메뉴 항목에 합성 `click()` 을 보내고, 이 클릭이 메뉴의 선택 핸들러를 거쳐 명령을 다시 부릅니다. 이 시점에는 조합이 이미 끝나 `isComposing = false` 라서 **즉시 실행**됩니다. → API 2회

두 구현은 서로의 존재를 모르고 있었습니다.

### 왜 다른 명령은 멀쩡해 보였나

사실 모든 슬래시 명령이 두 번 실행되고 있었습니다. 다만 "제목으로 바꾸기", "토글 만들기" 같은 에디터 내부 조작은 두 번 해도 결과가 같습니다(**멱등**). 서버에 새 리소스를 만드는 "페이지 생성"만 **비멱등**이라 두 번 실행된 흔적이 눈에 보였던 것입니다.

## 수정 방향 고르기

- **A. 경로 B(합성 클릭)를 지운다.** 바뀌는 파일이 1개이고, 명령 레이어의 래퍼는 17개 명령 전체에 이미 일관되게 적용돼 있습니다. 불안정한 DOM 합성 클릭 패턴도 함께 사라집니다.
- **B. 경로 A(래퍼)를 지운다.** 모든 명령 정의에서 래퍼를 벗겨야 해서 범위가 넓고, 합성 클릭에 계속 의존하게 됩니다.

A 를 골랐습니다. 단, **조합 중 Enter 를 막는 부분은 남겨야** 했습니다. 이것까지 지우면 메뉴 라이브러리가 조합 중인 Enter 를 직접 처리해 다른 문제가 생깁니다. 역할을 이렇게 나눴습니다.

- 메뉴 UI 레이어는 **이벤트 차단만** 합니다.
- 명령 레이어는 **실행만** 합니다.

```ts
if (e.isComposing) {
  if (e.key === 'Enter') {
    e.preventDefault(); e.stopPropagation(); e.stopImmediatePropagation();
    // pendingEnter = true;   ← 삭제
  }
  return;
}
// compositionend 의 selectedItem.click() 블록 ← 삭제
```

표 안에서 쓰는 별도 IME 처리는 다른 흐름이라 건드리지 않았습니다.

## 검증과 남은 것

- 실행 경로가 `compositionend → pendingCommand()` 한 곳으로 모이는 것을 코드로 확인했습니다. 지운 플래그를 참조하는 곳이 0건인 것도 확인했습니다.
- 원래 재현 케이스, 영문 입력, 표 안 입력, 링크 팝오버, 다른 명령까지 6개 시나리오를 점검했습니다.
- 다만 이 시점에는 **실제 브라우저에서 한글 IME 로 끝까지 돌리는 자동 테스트가 없었습니다.** 기존 빌드 오류 때문에 컴파일 단계 검증도 완전하지 않았습니다. 그래서 배포 전 수동 QA 를 조건으로 걸었습니다.

## 배운 점

- **"두 번 실행"은 서버보다 클라이언트 이벤트 흐름을 먼저 의심합니다.** 백엔드는 받은 요청을 정직하게 처리했을 뿐이었습니다.
- **같은 문제를 푸는 코드가 이미 있는지 먼저 찾습니다.** IME 처리를 추가하기 전에 `compositionend`, `isComposing` 을 grep 했다면 이중 구현을 피할 수 있었습니다.
- **멱등한 동작은 버그를 숨깁니다.** 테스트 시나리오에 반드시 비멱등 동작(서버 생성 API)을 넣어야 합니다.
- **한 관심사에는 소유자를 하나만 둡니다.** 차단하는 쪽과 실행하는 쪽을 나누면 이런 겹침이 생기기 어렵습니다.
- 중기적으로는 "실행 중" 플래그로 같은 명령의 중복 호출을 막는 가드를, 장기적으로는 IME 입력을 포함한 E2E 테스트를 남겼습니다.
