## 증상

"중복 로그인 방지" 정책을 켠 환경에서, 다른 기기로 로그인하면 기존 기기는 서버 DB 에서 **사용 중지**(`use_yn='N'`)로 바뀝니다. 그런데 그 기기의 브라우저 세션은 살아 있어서, 글 쓰기나 프로젝트 생성 같은 일반 API 가 **계속 200 으로 통과**했습니다.

더 곤란한 점은 기기 관리 화면이 "사용 중이고 최근 접속한 기기"만 보여준다는 것이었습니다. 무효화된 기기는 목록에서 사라지니, 사용자도 관리자도 이 상태를 볼 수 없었습니다. DB 상태는 "차단", 실제 접근은 "허용". 보안 관점에서 어긋난 상태였습니다.

## 재현

1. 기기 B 브라우저에서 로그인하고 탭을 닫는다.
2. 기기 A 로 로그인한다 → B 의 기기 인증이 `N` 이 된다.
3. B 에서 탭을 다시 연다 → 화면도 API 도 정상 동작한다.

DB 의 B 레코드는 `N` 이었고 이후 갱신도 없었습니다. 그런데 요청은 통과했습니다.

## 원인 추적

### 서버는 왜 못 막았나

요청 필터는 세션 쿠키와 사용자 ID 가 맞는지만 확인했습니다. 기기 인증이 살아 있는지는 **요청 1,000번 중 1번만** 확률적으로 DB 를 조회해 확인하고 있었습니다. DB 부하를 줄이려던 설계였습니다.

로그를 보니 반복 요청 중 샘플링이 걸린 기록이 거의 없었습니다. 탐지 코드는 있었지만 **사실상 발화하지 않았습니다.**

### 클라이언트는 왜 못 막았나

클라이언트에도 자기 검증 코드가 있었지만, 실시간 소켓의 connect 콜백에서만 실행됐습니다. 재현 상황에서는 소켓 요청이 응답 없이 걸려 있어 이 코드가 한 번도 돌지 않았습니다. 결국 **서버가 결정적으로 막아야 한다**는 결론이었습니다.

## 두 번 헛짚다

**1차 시도 — 세션 무효화 코드 추가.** 샘플링에 걸렸을 때 세션을 확실히 끊도록 고쳤습니다. 효과가 없었습니다. 끊는 코드는 맞았지만, 그 코드가 실행되는 조건(1/1000 확률)이 너무 드물었습니다.

**2차 시도 — 자동 로그인 경로 의심.** 브라우저 자동 로그인이 기기 인증을 검사하지 않고 세션을 되살린다고 보고 가드를 바꿨습니다. 그런데 재현 중 서버 로그를 2분간 확인하니 **그 경로 호출이 0건**이었습니다. 영향 범위만 넓히는 변경이라 되돌렸습니다.

두 번 모두 "코드만 보고 세운 가설"이었습니다. 세 번째부터는 가설마다 로그로 먼저 확인했습니다.

## 수정 방향 고르기

- **A. 세션에 30초 TTL 캐시를 두고, 캐시가 없으면 항상 DB 로 검증한다.** 결정적이고, 유령 세션이 살아 있는 시간의 상한이 30초로 정해집니다. 정상 사용자의 DB 조회는 30초에 1번으로 제한됩니다.
- **B. 기기 → 세션 역매핑 저장소를 만들어 차단 즉시(0초) 세션을 끊는다.** 저장소 신설과 동기화 비용이 큽니다. 보안 요구가 0초가 되면 이쪽으로 올리기로 기록했습니다.
- **C. 클라이언트에서 미리 확인한다.** 서버 방어선이 아니라 UX 개선입니다.

A 를 골랐습니다.

```java
boolean verifyDeviceCached(HttpServletRequest req, String user, String device) {
    HttpSession session = req.getSession(false);
    if (session != null) {
        // "user|device" 지문이 다르거나 30초가 지났으면 null
        Boolean cached = cache.get(session, user, device, TTL_30S);
        if (cached != null) return cached;
    }
    boolean ok = verifyDeviceFromDb(user, device);   // 샘플링 없이 항상 조회
    if (session != null) {
        try { cache.set(session, user, device, ok); } catch (Exception ignore) { }
    }
    return ok;
}
```

- 캐시에 결과만 넣지 않고 **`사용자|기기` 지문**을 함께 넣었습니다. 세션이 다른 사용자로 재사용될 때 캐시가 오염되는 것을 막습니다.
- 세션이 없어 새로 만드는 경로는 캐시 없이 항상 DB 를 봅니다.
- 세션에서 사용자를 제거할 때 캐시 값도 함께 지웁니다.

## 비용 검증: 부하 테스트

"모든 요청에서 검증한다"는 말이 DB 를 두드리는 것처럼 들려서, 개발 환경에서 부하 테스트로 확인했습니다.

- 19분 동안 92,399건 처리, 실패 0
- DB 의 기기 인증 조회 흔적: **164회** → 캐시 hit 율 **99.82%**
- 지연 p50 9.6ms, p95 17.9ms, 최대 150 RPS
- 운영 규모로 환산한 추가 DB 조회는 초당 약 2.3건. 기존 1/1000 샘플링(초당 약 2.2건)과 **사실상 같은 수준**이었습니다.

사전에 "활성 사용자 수 ÷ TTL" 로 계산한 상한은 동접 1만 기준 초당 +333건이었습니다. 실측은 그보다 훨씬 낮았습니다. 같은 사용자의 요청이 30초 안에 몰리기 때문입니다.

부하 테스트에서 배운 실무 팁도 있습니다.

- 대시보드 같은 무거운 API 는 30 RPS 에서 p95 가 40초까지 치솟아 측정을 방해했습니다. **중간 무게의 단순 조회 API** 를 고르는 것이 중요했습니다.
- 부하 도구의 쿠키 저장소가 세션을 하나로 합쳐 버려서, 로그인 호출마다 초기화해야 했습니다.
- 개발 환경에서 디버그 로그가 꺼져 있어, SQL 흔적 개수로 조회 횟수를 간접 측정했습니다.

## 결과와 남은 것

- 유령 세션 지속 시간: 사실상 무제한(샘플링이 걸릴 때까지) → **최대 30초**
- 남은 것: 관리자가 기기를 다시 승인해도 최대 30초 동안은 차단 캐시가 남습니다. 0초가 필요해지면 B 안으로 올립니다.

## 배운 점

- **"탐지 코드가 있다"와 "탐지가 발화한다"는 다릅니다.** 확률 샘플링은 보안 경로에 맞지 않습니다.
- **가설은 로그로 기각합니다.** 코드만 보고 고친 두 번이 모두 헛짚었고, 로그 0건 하나가 2차 가설을 정리해 줬습니다.
- **캐시 TTL 의 DB 부하는 "활성 사용자 ÷ TTL" 이 상한**입니다. 실제로는 훨씬 낮으니 실측으로 확인합니다.
- 운영에 부하를 보내는 대신, 개발 환경 실측에 인스턴스 규모 비율을 곱해 외삽했습니다.
