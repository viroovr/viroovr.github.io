## 증상

업무 목록 화면에서 **상태 필터를 걸고 그룹으로 묶어 보면** 로딩 스켈레톤이 끝나지 않는다는 보고가 들어왔습니다. 같은 필터라도 그룹화를 끄면 정상이었고, 간트 차트 화면도 똑같이 멈췄습니다. 고객 지원 쪽에서 다른 계정으로 따라 해 보면 재현이 안 됐습니다. **데이터에 따라서만 터지는 문제**였습니다.

## 관측 사실

문제 계정의 데이터부터 셌습니다.

- 참여 중인 프로젝트 2,449개
- 본인이 담당한 업무 5,394건 (290개 프로젝트에 흩어져 있음)
- 22개 프로젝트가 **사용자 정의 상태 컬럼**을 쓰고 있었고, 선택지는 모두 44개

서버 로그에는 그룹 목록 SQL 이 `statement_timeout`(35초)에 걸려 취소된 기록이 있었습니다. 취소된 뒤에는 예비 쿼리가 다시 돌아 0.5~8초가 더 걸렸고, API 응답은 결국 **36~43초 뒤**에 나갔습니다. 그사이 프론트엔드에는 실패 처리가 없어서 스켈레톤이 그대로 남아 있었습니다.

## 원인

상태 필터는 SQL 에서 이런 모양이 됩니다.

```sql
-- 기본 상태 코드 OR 사용자 정의 상태 값
AND ( t.status IN ('REQUEST', 'PROGRESS')
   OR EXISTS (SELECT 1 FROM custom_field_value v
               WHERE v.task_id = t.id AND v.option_id IN (...44개)) )
```

그룹 목록 쿼리는 프로젝트를 먼저 21개 뽑고(프리페치), 프로젝트마다 `LATERAL` 서브쿼리로 업무를 세는 구조였습니다. 문제는 이 `OR` 이었습니다.

1. **OR 때문에 상태 인덱스를 못 탔습니다.** 두 조건 중 하나만 맞아도 되니, 플래너는 `status` 인덱스로 범위를 줄이지 못했습니다.
2. **플래너가 담당자 테이블에서 출발했습니다.** 추정 행 수는 918건이었지만 실제로는 5,394건이었고, 프로젝트마다 이것을 반복하면서 약 **1,320만 번의 탐색**이 일어났습니다.
3. **담당자 조건이 너무 늦게 평가됐습니다.** 담당자 필터(`IN` 목록)로 2,449개 프로젝트를 7개로 줄일 수 있었는데, 이 조건이 `EXISTS` 뒤에 평가돼 아무것도 줄이지 못했습니다.

`EXPLAIN ANALYZE` 로 확인한 숫자는 이렇습니다.

- 기본 상태 조건만 사용: 7,048ms
- 기본 상태 OR 사용자 정의 상태: **35초 타임아웃**

같은 화면의 목록·개수 쿼리는 예전에 같은 패턴으로 이미 고쳐 둔 상태였습니다. **그룹 경로만 빠져 있었던 것**입니다.

## 수정 방향 고르기

세 가지를 비교했습니다.

- **A. 대상 업무를 CTE 로 먼저 확정한다.** 담당자와 상태 조건을 만족하는 업무를 한 번만 계산해 두고, 프로젝트 루프는 그 결과 위에서만 돈다.
- **B. OR 를 UNION 으로 다시 쓴다.** 모든 화면에 공통으로 쓰는 조건이라 영향 범위가 넓고, 결과가 같다는 것을 증명하기 어렵다.
- **C. 타임아웃을 늘리거나 LIMIT 를 줄인다.** 다른 보호 장치를 깨거나 결과가 달라지므로 기각했다.

A 를 골랐습니다. 원인(프로젝트마다 같은 조건을 반복 평가)을 직접 없애고, 이미 같은 방식으로 고친 목록 쿼리가 있어 검증 기준을 재사용할 수 있었기 때문입니다. 프론트엔드에서 실패 시 스켈레톤을 풀어 주는 안전망은 별도 작업으로 분리했습니다.

## 1차 수정

```sql
WITH my_task AS MATERIALIZED (
  SELECT DISTINCT t.id, t.project_id
    FROM task_assignee a
    JOIN task t ON t.id = a.task_id
   WHERE a.user_id IN (...)
     AND <상태 OR 조건 등 나머지 필터>
)
SELECT ...
  FROM project p
 WHERE p.id IN (SELECT project_id FROM my_task)
 ...
```

- `MATERIALIZED` 로 CTE 를 한 번만 계산하게 고정했습니다.
- **권한 조건은 CTE 안에 넣지 않았습니다.** 넣어 봤더니 플래너가 참여 중인 모든 프로젝트의 게시물을 먼저 펼쳐서 2.7초가 걸렸습니다. 바깥에서 업무별로 검사하면 충분했습니다.
- 코드 리뷰에서 `DISTINCT` 가 빠진 문제가 발견됐습니다. 담당자를 2명 이상 고르면 한 업무가 조인에서 두 번 나와 **그룹별 개수가 부풀었습니다.** 기존 `EXISTS` 는 세미조인이라 이런 문제가 없었습니다.
- 기능 플래그(기본 OFF) 뒤에 넣어서, 문제가 생기면 코드 롤백 없이 끌 수 있게 했습니다.

결과가 같은지는 수정 전후 결과 행 전체를 `md5(string_agg(... ORDER BY ...))` 로 해시해서 비교했습니다. 원래 재현 케이스는 **35초 타임아웃 → 64ms** 로 줄었고, 결과 해시도 같았습니다.

## 그런데 다른 케이스가 느려졌다

스테이징에서 조건을 바꿔 가며 재보니 **담당자만 넓게 걸고 상태 필터는 없는 경우**가 오히려 느려졌습니다.

- 기존: 첫 호출 62.7초(타임아웃 후 예비 쿼리), 이후 2.2초
- 1차 수정: 6.7~6.9초

실행 계획을 보니 플래너가 프로젝트의 업무를 먼저 읽고, **업무 하나마다 CTE 전체(2,612행)를 순차 스캔**하고 있었습니다. CTE 결과에는 인덱스가 없기 때문입니다. 12,021번 × 2,612행이었습니다. 처음 케이스는 상태 필터 덕분에 CTE 가 20행뿐이라 이 문제가 드러나지 않았던 것입니다.

## 2차 수정

프로젝트별로 CTE 에서 먼저 업무 id 를 뽑고, 원본 테이블은 기본 키로 조인하게 바꿨습니다.

```sql
FROM (SELECT mt.id FROM my_task mt
       WHERE mt.project_id = p.id
      OFFSET 0) mt          -- OFFSET 0: 서브쿼리를 펼치지 못하게 막는 울타리
JOIN task t ON t.id = mt.id
```

- 담당자만 건 케이스: 9.87초 → **0.21초** (실행 계획 기준)
- 스테이징 실측: 담당자+상태 0.85초 → **0.15~0.31초**, 담당자만 첫 호출 62.7초 → **2.1초**, 이후 0.26~0.29초
- 모든 케이스에서 결과 해시가 같았습니다.

## 배운 점

- **OR 는 인덱스를 무력화하기 쉽습니다.** 특히 상관 서브쿼리 안에서 반복되면 비용이 프로젝트 수만큼 곱해집니다.
- **CTE 는 인덱스가 없는 임시 결과입니다.** CTE 를 조인의 안쪽에 두면 바깥 행마다 전체 스캔이 됩니다. 바깥 키로 먼저 걸러서 꺼내는 모양이 안전합니다.
- **고친 케이스만 재면 안 됩니다.** 원래 재현 케이스는 64ms 였지만, 필터 조합을 바꾸자 회귀가 보였습니다. 조건 조합별 측정표를 먼저 만들어 두는 것이 좋았습니다.
- **측정 실수도 기록해 둡니다.** 대조 쿼리에서 정렬 전에 `row_number() OVER ()` 로 상위 20행을 잘라 합계가 어긋난 적이 있습니다. 순번은 최종 정렬 뒤에 매겨야 합니다.

## 다음에 같은 증상이 오면

1. "특정 계정에서만 무한 로딩"이면 DB 타임아웃 로그와 그 계정의 데이터 규모부터 센다.
2. 같은 파라미터로 `EXPLAIN (ANALYZE, BUFFERS)` 를 돌리고, 추정 행 수와 실제 행 수가 크게 다른 노드를 찾는다.
3. `OR`, `EXISTS`, `LATERAL` 이 겹친 곳에서 루프 횟수 × 행 수를 계산해 본다.
4. 수정 전후 결과를 해시로 비교하고, 필터 조합을 바꿔 가며 회귀를 확인한다.
