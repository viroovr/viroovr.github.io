## 증상

외부 연동용 API 서버의 CPU 가 갑자기 100% 가 됐습니다. 응답이 느려졌고, 재시작해야만 회복됐습니다.

## 좁혀 들어가기

증상(CPU)에서 출발해 GC → 메모리 → 프레임워크 동작 → 우리 코드 한 줄 순서로 내려갔습니다.

### 1. CPU 를 쓰는 것은 GC 였다

`sar -u` 로 언제부터 올랐는지 보고, `jstat -gcutil` 로 GC 상태를 봤습니다.

- Old 영역 사용률 **100%** 고정
- Full GC 누적 410회. 한 번에 약 5.7초씩 걸렸고, 9분 동안 19번 돌았습니다. **시간의 약 24% 가 GC 정지**였습니다.
- Full GC 를 돌려도 회수되는 메모리가 거의 없었습니다. 살아 있는 객체가 힙을 채우고 있다는 뜻입니다.

### 2. 무엇이 Old 를 채웠나

`jmap -histo` 상위 클래스를 봤습니다.

- **요청 컨텍스트 객체 368만 개**
- 그리고 거기 딸린 자원 관리자, DB 연결 래퍼, 맵 객체들이 **정확히 같은 개수**로 묶여 있었습니다.

개수가 1:1 로 묶인 클래스 묶음은 "한 객체가 나머지를 붙잡고 있다"는 강한 신호입니다.

### 3. 요청 수와 맞아떨어지는가

재시작한 JVM 에서 61초 동안 컨텍스트 객체가 **655개** 늘었습니다. 같은 시간 알림 API 호출은 **641건**이었습니다. 요청 하나당 하나씩 새고 있었습니다.

### 4. 왜 안 사라지나

`javap -p` 로 프레임워크 클래스를 열어 봤습니다. 이 컨텍스트는 생성될 때 **static 풀에 자기 자신을 등록**하고, `close()` 가 불려야만 풀에서 빠집니다. 누군가 `close()` 를 빠뜨리면 영원히 남습니다.

### 5. 누가 안 닫나

외부 API 진입점(게이트웨이)의 흐름을 따라갔습니다.

1. 액션을 실행하기 전에 **API 키 검사와 로그 기록**을 위해 DB 를 씁니다. 이때 컨텍스트가 하나 만들어집니다.
2. 그다음 액션 실행부가 새 컨텍스트를 만들면서 **앞의 것을 닫지 않고 덮어씁니다.**
3. 덮어써진 컨텍스트는 static 풀에만 남아 → 요청 1건당 1개 누수.

결정적인 단서는 **구조가 같은 형제 게이트웨이**였습니다. 그쪽은 액션 전에 컨텍스트를 먼저 정리(free)하고 있었고, 누수가 없었습니다.

## 재현

테스트 서버에서 게이트웨이로 요청을 보냈습니다.

- 요청 21,013건 → 누수 객체 **21,004개** (1:1)
- 수정 후 200건 호출 → 19개, 더 늘지 않음

운영에 넣기 전에 "요청 N건 = 누수 N개"를 확인한 것이 확신의 근거가 됐습니다.

## 재발 시점 예측

누수 속도(초당 6.5~10.7개)와 힙 크기로 계산하면 **약 5~6일 뒤 힙이 다시 가득 찰** 것이었습니다. 운영 추세를 보고 "10월 19일 저녁 전후 재발"을 예측했고, 실제로 19일 오후에 재발했습니다. 배포 브랜치가 운영 브랜치 전환과 맞물려 늦어지는 바람에, 예측한 재발을 한 번 겪고 나서야 수정이 나갔습니다.

## 수정

```diff
+        freeContext();   // 키 검사·로그용 DB 호출이 만든 컨텍스트를 액션 전에 닫는다
         result = performAction(apiKey, request, response);
```

- 형제 게이트웨이와 같은 방식으로, **한 줄**을 추가했습니다.
- 바이트코드를 비교해 원본과의 차이가 이 호출 하나뿐인 것을 확인했습니다.
- 다른 대안(컨텍스트 생성 순서 변경, 프레임워크 jar 수정)은 영향 범위가 넓어서 제외했습니다.
- 롤백은 `.class` 파일 하나만 되돌리면 됩니다.

## 결과 (배포 16.9시간 후)

- 컨텍스트 객체: 수정 전 속도라면 40~65만 개였을 시점에 **18,709개**
- 누수 속도: 초당 6.5~10.7개 → **초당 약 0.39개** (남은 것은 별개의 작은 2차 경로)
- Old 영역: 장애 직전 100% → **37%**

## 아쉬웠던 점

- **처음에 프레임워크 코드를 잘못 읽었습니다.** "보통은 새지 않는다"고 기록했다가 정정했습니다. 추측하지 말고 처음부터 `javap -c` 로 바이트코드를 직접 확인했어야 했습니다.
- **GC 로그가 없었습니다.** 장애가 시작된 순간의 상황은 직접 볼 수 없었습니다.

## 배운 점

- **CPU 100% 가 항상 "코드가 바쁘다"는 뜻은 아닙니다.** Old 영역이 고정돼 있다면 GC 가 CPU 를 먹고 있는 것입니다.
- **히스토그램에서 개수가 같은 클래스 묶음을 찾으면** 누수의 주인을 빨리 찾을 수 있습니다.
- **같은 구조인데 문제가 없는 형제 코드**가 가장 좋은 정답지입니다.
- **누수 속도를 알면 재발 시점을 계산할 수 있습니다.** 조기 경보 지표(Old 사용률, 의심 객체 수)를 주기적으로 수집하면 장애 전에 대응할 수 있습니다.

## 다음에 같은 증상이 오면 (런북)

1. `sar -u` 로 언제부터인지, `jstat -gcutil` 로 GC 때문인지 함께 본다.
2. Old 가 고정되고 FGC 가 계속 늘면 → `jmap -histo:live` 상위 20개에서 같은 개수로 묶이는 클래스를 찾는다.
3. 그 주인 클래스가 static 컬렉션에 등록되는지 `javap -p` 로 확인하고, 빠지는 조건(`close`)을 누가 빠뜨리는지 추적한다.
4. 구조가 같은데 누수가 없는 형제 코드와 비교한다.
5. 테스트 서버에서 "요청 N건 → 객체 N개"를 재현한 뒤 수정 전후를 비교한다.
6. 운영 JVM 에는 GC 로그와 `-XX:+HeapDumpOnOutOfMemoryError` 를 미리 켜 둔다.
