형제 노드보다 CPU 가 3배 — JSON 직렬화기의 제곱 비용 찾기

같은 역할의 서버 두 대를 비교해 원인을 좁히고, 이미 만들어져 있던 수정을 운영까지 끌고 간 기록

2026년 10월 22일 · 4분 읽기 · #troubleshooting · #performance · #jvm

증상

같은 역할을 하는 WAS 노드 두 대 중 한 대(노드 A)만 java 프로세스 CPU 가 약 300% 였습니다. 옆 노드 B 는 108% 였고, 요청량 차이는 13% 뿐이었습니다. 응답 지연이나 요청 적체는 없었습니다. 대신 메모리 할당이 초당 약 3GB 였고, Young GC 가 약 3초마다 돌고 있었습니다.

예전에 다른 노드에서도 같은 증상이 있었지만, 원인을 못 찾은 채 저절로 사라진 적이 있었습니다.

가설 지우기

두 노드를 같은 시간대에 나란히 놓고 하나씩 지웠습니다.

  • GC 스레드? GC 스레드가 쓰는 CPU 는 4~5% 뿐이었습니다.
  • 스레드 수? 두 노드가 비슷했습니다.
  • JIT 컴파일? 해당 없었습니다.
  • 스레드별 CPU 를 보니 요청 처리 스레드가 CPU 의 93% 를 쓰고 있었습니다. 요청을 처리하는 코드 자체가 무거웠던 것입니다.

프로파일링

async-profiler 로 30초 동안 CPU 샘플을 떴습니다. 가장 두드러진 경로는 JSON 직렬화였습니다.

toJSONString()
  └ StringBuilder.toString()   ← 배열 복사, 전체 샘플의 약 14%

직렬화기가 배열에 항목을 하나 쓸 때마다 지금까지 쌓인 버퍼 전체를 문자열로 복사하고 있었습니다. 항목이 n 개면 복사량이 1 + 2 + … + n, 즉 응답 크기의 제곱에 비례합니다. 응답이 작을 때는 티가 안 나다가, 큰 응답에서 급격히 무거워지는 구조입니다.

왜 노드 A 만?

직렬화 코드는 모든 노드에 똑같이 들어 있습니다. 그런데 왜 A 만 심했을까요?

액세스 로그에서 URL 별 응답 바이트 합계를 냈습니다. 요청 수가 아니라 바이트로 본 것이 핵심이었습니다.

  • 채팅 메시지 조회 API 응답량: 노드 A 108MB, 노드 B 58MB
  • 노드 A 의 이 트래픽 중 약 80% 가 PC 클라이언트 한 곳에서 왔습니다. 약 100KB 짜리 채팅 기록을 하루 4만 번 반복해서 가져가고 있었습니다.
  • 로드밸런서가 세션 고정(sticky session)이라, 이 클라이언트의 요청이 계속 노드 A 로만 갔습니다.

즉 비용 자체는 모든 노드에 깔려 있었고, 노드 A 는 큰 응답을 반복 요청하는 클라이언트 때문에 유독 두드러졌을 뿐이었습니다.

수정은 이미 있었다

코드를 고치려고 보니, 동료가 같은 낭비 복사를 없앤 수정을 2주 전에 개발 브랜치에 머지해 둔 상태였습니다. 다만 운영 브랜치에는 아직 들어가지 않았습니다.

그래서 이번 작업은 “고치기”가 아니라 “이미 있는 수정을 원인과 연결해 운영까지 보내기” 였습니다.

  1. 수정 커밋이 운영 브랜치의 조상에 없는지 확인했습니다.
  2. 핫픽스 트랙으로 cherry-pick 했습니다.
  3. 배포 전에 기준선을 저장했습니다. APM 보관 기간이 약 7일이라, 늦으면 비교할 수치가 사라지기 때문입니다.
  4. 배포 후 실제로 서빙 중인 .class 파일의 md5 와 JVM 시작 시각을 확인했습니다. “배포했다”는 말이 아니라 실제 바이너리를 확인한 것입니다.

함정: 재시작 직후 수치

배포 직후 수치를 보니 오히려 20~30% 나빠진 것처럼 보였습니다. JVM 재시작 직후에는 JIT 컴파일이 덜 된 상태라 같은 코드도 느리게 돕니다. 그래서 판정을 보류하고, 다음 날 같은 시간대 3개 구간을 다시 재서 비교했습니다.

결과

  • 프로파일러에서 문제 경로 샘플: 424 → 0
  • 전체 CPU 중 직렬화 비중: 15% → 1%
  • 요청당 메모리 할당: 73~96% 감소
  • 채팅 API 의 요청당 할당: 약 115~215MB → 약 7MB
  • 운영 WAS 15대 전체: 요청당 CPU 16~26% 감소, 요청당 GC 시간 41~57% 감소 (평소 일간 변동은 ±4%)

한 노드의 이상 증상을 쫓다가, 결국 전체 노드의 비용을 줄인 셈입니다.

배운 점

  • 형제 노드 비교는 강력한 도구입니다. 같은 코드, 같은 역할인데 한쪽만 다르면, 차이는 입력(트래픽)에 있습니다.
  • 요청 수가 아니라 응답 바이트로 봐야 할 때가 있습니다. 요청 수는 13% 차이였지만, 응답량은 거의 2배였습니다.
  • 기준선은 서버별 원본 값으로, 배포 전에 저장합니다. 집계값만 남기면 나중에 다른 기준으로 다시 볼 수 없습니다. 운영이 아닌 서버는 집계에서 뺍니다.
  • 재시작 직후 수치로 판정하지 않습니다. JIT 워밍업이 끝난 뒤, 같은 요일·같은 시간대끼리 비교합니다.
  • 성능 수정은 머지가 아니라 운영 반영까지 추적합니다. 수정이 2주 동안 운영에 안 들어가 있었다는 것이 이번 일의 진짜 원인이었습니다.

다음에 같은 증상이 오면

  1. 이상한 노드와 정상 노드를 같은 시간대에 나란히 놓는다.
  2. GC 스레드 / 요청 스레드 / 기타로 CPU 를 나눈다.
  3. 요청 스레드라면 프로파일러로 30초 샘플을 뜬다.
  4. 액세스 로그를 URL 별 바이트로 집계해 두 노드를 비교한다.
  5. 수정이 이미 있는지, 있다면 운영 브랜치에 들어갔는지부터 확인한다.
