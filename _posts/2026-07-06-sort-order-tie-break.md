## 증상

위키의 사이드바에서 페이지를 드래그해 순서를 바꾸면, 새로고침했을 때 **어떤 때는 옮겨져 있고 어떤 때는 원래 자리**였습니다. 특정 위치로 옮기려 하면 아예 에러 토스트가 뜨기도 했습니다.

## "새로고침마다 다르다" 는 신호

새로고침 후 보이는 것은 서버가 조회한 결과입니다. 프론트엔드 상태가 늦게 반영되는 문제였다면 새로고침하면 결과가 항상 같아야 합니다. 저장이 실패했다면 항상 원래 자리여야 합니다. **"때때로"** 는 이 두 가설로 설명되지 않습니다.

같은 요청에 다른 결과가 나온다면, 먼저 **정렬의 비결정성**을 의심합니다.

## 관측 사실

정렬은 이렇게 되어 있었습니다.

- 형제 노드 사이의 순서는 문자열 **fractional indexing** 키(`sort_order`)로 정합니다. 두 노드 사이에 넣을 때 `generateKeyBetween(a, b)` 로 중간 키를 만듭니다.
- 조회는 `ORDER BY sort_order COLLATE "C" ASC` **단일 키**였습니다.
- `generateKeyBetween(a, b)` 는 `a == b` 이면 예외를 던집니다.
- 새 문서를 만들 때 형제가 없거나, 형제 조회가 누락되거나, 동시에 두 개가 만들어지면 `generateKeyBetween(null, null)` 이 항상 **`'a0'`** 을 돌려줍니다.

코드를 더 보기 전에 운영 DB 를 읽기 전용으로 조회했습니다.

```sql
SELECT parent_id, sort_order, count(*)
  FROM document
 GROUP BY parent_id, sort_order
HAVING count(*) > 1;
```

- 신고자의 폴더 아래 문서 3개가 **모두 `'a0'`** 이었습니다.
- 전체로는 문서 27개 그룹(초과 행 131개), 폴더 15개 그룹에서 중복이 있었습니다.
- 마이그레이션으로 들어온 옛 데이터뿐 아니라 최근 데이터에도 섞여 있었습니다. **지금도 만들어지고 있다**는 뜻입니다.

## 원인

- **읽기 쪽:** 정렬 키가 같은 행들의 순서를 PostgreSQL 은 보장하지 않습니다. 물리적 위치나 실행 계획에 따라 매번 달라질 수 있습니다. 그래서 새로고침마다 순서가 뒤집혔습니다.
- **쓰기 쪽:** 키가 같은 두 이웃 사이로 드롭하면 `generateKeyBetween('a0', 'a0')` 가 예외를 던져 이동이 실패했습니다.
- **근본:** 형제 사이 정렬 키는 유일해야 한다는 **계약이 있었지만 스키마에 강제 장치가 없었습니다.** "마지막 형제를 조회하고 키를 계산" 하는 과정도 원자적이지 않았습니다.

## 수정 방향 고르기

- **A. 읽기에 tie-break 만 추가.** 가장 안전하지만, 같은 키 사이 드롭 예외와 기존 중복 데이터, 재발이 그대로 남습니다.
- **B. 유니크 부분 인덱스 + 충돌 시 재시도.** 동시성까지 확실히 막습니다. 하지만 루트 노드의 부모가 NULL 이라 `NULLS NOT DISTINCT`(PostgreSQL 15+)가 필요하고, 기존 중복을 먼저 정리해야 인덱스를 만들 수 있습니다. 운영 QA 수정으로는 과해서 후속으로 미뤘습니다.
- **C. 스키마 변경 없이 네 겹으로 막는다.** 채택.

```ts
// 1) 읽기: 모든 sort_order 정렬에 PK 를 2차 키로 → 순서 고정
qb.orderBy('item.sortOrder COLLATE "C"', 'ASC')
  .addOrderBy('item.id', 'ASC');

// 2) 이동: 이웃 키가 같으면 예외 대신 뒤쪽 키를 만든다
function between(a, b) {
  const [min, max] = a < b ? [a, b] : [b, a];
  if (min === max) return generateKeyBetween(min, null);
  return generateKeyBetween(min, max);
}

// 3) 생성: 형제 키와 겹치면 유일해질 때까지 밀어낸다 (시도 상한: 형제 수 + 1)
sortOrder = await ensureUniqueSortOrder(computed, siblings);

// 4) 정리: 중복이 있는 부모만, 현재 표시 순서 (sort_order, id) 를 보존한 채
//    generateNKeysBetween(null, null, N) 으로 키를 다시 부여 (멱등)
```

각 층의 역할은 이렇습니다.

- 읽기 tie-break 는 중복이 있어도 **무해하게** 만듭니다.
- 이동 폴백은 중복 위에서도 동작을 **성공**시킵니다.
- 생성 시 충돌 회피는 새 중복을 **줄입니다**.
- 마이그레이션은 기존 중복을 **정리**합니다.

정렬 지점이 18곳 정도라 grep 으로 `COLLATE "C"` 를 쓰는 모든 정렬에 tie-break 가 붙었는지 확인했습니다. 메모리에서 다시 정렬하는 경로에도 같은 2차 키를 넣었습니다.

## 검증

- **성능:** 정렬 키를 `(sort_order)` 에서 `(sort_order, id)` 로 늘려도 실행 계획은 그대로였습니다(Index Scan → Sort, cost 동일). 새 Sort 나 Seq Scan 이 생기지 않았습니다. **결정적 정렬은 사실상 공짜**였습니다.
- **엣지:** 같은 키 사이 삽입이 더 이상 예외를 던지지 않습니다. 정상 경로(`min < max`)는 바뀌지 않습니다. 마이그레이션은 중복이 0이면 아무것도 하지 않습니다.
- **리뷰에서 잡힌 것:** 메모리 정렬에서 bigint ID 를 `Number()` 로 비교하고 있었습니다. 2^53 을 넘으면 정밀도가 깨지므로 `BigInt` 비교로 바꿨습니다.
- 솔직하게 적으면, 새로고침을 반복해 순서가 안정됐음을 E2E 로 확인한 기록은 없습니다. 이 수정은 **구조적으로 비결정성을 없앤 것**입니다.

## 후일담

두 달 뒤 다시 조회해 보니 중복 그룹이 오히려 문서 493개, 폴더 81개로 늘어 있었습니다. 동시 생성 경합이 계속 중복을 만들고 있다는 뜻입니다. tie-break 덕분에 사용자에게는 보이지 않지만, 원천 차단은 결국 유니크 인덱스(B 안)가 필요합니다.

## 배운 점

- **"간헐적", "새로고침마다" 는 비결정성의 신호입니다.** 정렬과 집합 연산의 tie-break 부터 확인합니다. 이 한 단어로 UI 갱신 가설을 일찍 접을 수 있었습니다.
- **데이터 결함은 코드보다 DB 를 먼저 봅니다.** `GROUP BY ... HAVING count(*) > 1` 한 번으로 5분 만에 확증했습니다.
- **유일성이 계약이면 스키마로 강제합니다.** 애플리케이션 계층만으로는 동시성 중복을 완전히 막을 수 없어서, 무해화·치유·정리를 겹겹이 둬야 했습니다.

## 체크리스트

- 새 `ORDER BY sort_order` 에는 PK 를 2차 키로 붙인다.
- bigint ID 는 `Number()` 로 비교하지 않는다.
- 데이터 정리 마이그레이션은 부모 단위로, 현재 표시 순서를 보존하고, 멱등하고, NULL 에 안전하게 만든다.
