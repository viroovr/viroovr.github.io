썸네일이 정확히 30초 — 캐시 용량이 아니라 키 인덱스가 꽉 차 있었다

30초 타임아웃 밴드에서 출발해 이미지 변환 서버의 nginx 캐시 keys_zone 상한을 찾아내고, 계층별 타임아웃을 다시 맞춘 기록

2026년 8월 28일 · 5분 읽기 · #troubleshooting · #performance · #infra

증상

APM 의 응답시간 산점도에 30.1~30.8초 구간에 점들이 띠처럼 이어져 있었습니다. 전부 썸네일 이미지 요청이었습니다.

트랜잭션 하나를 열어 보니:

  • 전체 30,068ms 중 CPU 10ms, SQL 5ms
  • 외부 HTTP 호출 30,053ms — 시간의 99.9% 가 이미지 변환 서비스의 응답을 기다리는 데 쓰였습니다.
  • 에러는 SocketTimeoutException: Read timed out. 응답 헤더를 읽는 단계에서 멈췄습니다. 바디를 받다가 끊긴 게 아니라, 상대가 아무것도 보내지 않은 상태였습니다.

SQL 이 짧고 외부 호출이 전체를 차지한다면, 조사 대상은 이 서버가 아니라 호출받는 쪽입니다.

첫 판단을 정정하다

처음에는 “썸네일 요청이 30초씩 스레드를 잡아서 WAS 전체가 밀린다”고 봤습니다. 대시보드를 다시 보니 아니었습니다.

  • 요청 처리량(TPS)은 평탄했고 떨어지지 않았습니다.
  • 서버당 동시 처리 중인 요청은 1~11건으로, 스레드 풀 대비 한 자릿수 % 였습니다.

스레드 하나가 30초씩 묶이는 것은 맞지만, 풀이 고갈된 것은 아니었습니다. 이 정정이 뒤에서 타임아웃 값을 정하는 근거가 됩니다.

이미지 변환 서버에서 본 것

변환 서버는 2 vCPU 인스턴스 1대에 Node 프로세스 8개, 앞에 nginx 캐시가 있는 구조였습니다.

  • 장애 시각 1분 load average 37.00, run queue 22. 그런데 CPU idle 은 약 50% 였습니다.
  • 받은 트래픽 대비 보낸 트래픽이 약 78:1. 요청이 거의 전부 캐시 미스였다는 정황입니다.
  • 8월 영업일 최대 load 는 매일 10~26. 이날만 그런 게 아니라 평소에도 과부하였습니다.
  • 캐시 HIT 0.15ms, MISS 약 35ms. 233배 차이입니다.

그리고 캐시 상태가 이상했습니다.

  • 설정: keys_zone=20m, max_size=20g
  • 캐시 엔트리 142,557개 — keys_zone 20MB 가 담을 수 있는 키 수(약 16만)의 89%
  • 캐시 디스크 사용량은 1.5GB — max_size 의 7.5%
  • 22시간 동안 엔트리가 64개 늘었습니다.

용량은 텅 비어 있는데 엔트리 수가 멈춰 있었습니다. 키 인덱스가 꽉 차서, 하나를 넣을 때마다 하나를 버리고 있었던 것입니다(LRU 상시 축출). 오래된 게시물의 이미지는 거의 항상 미스가 났습니다.

설정 주석에는 “이미지 1개당 100KB” 라는 가정으로 max_size 를 잡았다고 적혀 있었습니다. 실제 평균은 약 11KB 로 9배 작았습니다. 그래서 의도한 상한(디스크 용량)이 아니라 의도하지 않은 상한(키 개수)이 먼저 걸렸습니다.

기각한 후보들

  • 변환 앱 크래시 — 8개 프로세스 모두 LISTEN, accept 큐 0, 평시 35ms.
  • 최근 배포(이미지 회전 처리 추가)의 회귀 — 배포 전 날짜의 부하가 배포 후보다 더 높은 날이 있었습니다.
  • 거대 이미지 하나 — JPEG 은 65KB 든 802KB 든 처리시간이 약 36ms 로 같았습니다(libvips 의 shrink-on-load). PNG 는 측정하지 못했습니다.
  • 디스크, 로그, 임시 파일 — 평시 디스크 사용률 0.4%, 로그 합계 14일에 3.5MB, 삭제된 fd 0건.

자가 증폭 가능성

WAS 는 30초에 포기하지만, 변환 서버 앞 nginx 의 proxy_read_timeout 은 5분이었습니다. 아무도 기다리지 않는 요청이 계속 CPU 를 점유해 큐가 스스로 빠지지 않았을 가능성이 큽니다. 실측이 아니라 설정에서 나온 추정입니다.

30초가 특히 나빴던 이유

CDN 의 원본 응답 타임아웃도 30초였습니다. WAS 가 30초 만에 포기하고 원본 이미지로 폴백할 때는 CDN 이 이미 연결을 끊은 뒤였습니다(로그에 Broken pipe). 폴백이 있어도 사용자에게는 깨진 썸네일이 보였습니다.

수정

이미지 변환 서비스 (근본 원인)

  • keys_zone 20MB → 256MB. 일을 줄이는 유일한 방법입니다(HIT 과 MISS 가 233배 차이). 키 인덱스(약 200만 키)보다 max_size 가 먼저 걸리도록 계산해 맞췄습니다.
  • 업스트림 타임아웃 read 5분 → 10초, connect 1초. 재시도 2회, 재시도 총 시간 10초.
  • 업스트림 8개에 max_fails=2 fail_timeout=10s — 멈춘 프로세스를 라운드로빈에서 뺍니다.
  • 이미지 라이브러리 내부 스레드를 1로 고정했습니다.
  • 커밋 3개로 나눠 하나씩 되돌릴 수 있게 했습니다.

배포 순서도 중요했습니다. 페일오버 설정을 먼저 넣고, 그다음 프로세스를 재시작했습니다. 반대로 하면 재시작 구간마다 502 가 새어 나갑니다.

WAS (호출자 방어)

  • 변환 호출 타임아웃을 connect 30초 → 1초, read 30초 → 5초로 줄이는 패치를 준비했습니다.
  • 3초가 아니라 5초를 고른 이유: 병목이 스레드가 아니었으니 스레드를 빨리 돌릴 이유가 없었습니다. 너무 짧으면 폴백만 늘어납니다.
  • 계층 간 순서를 맞췄습니다: CDN 30초 > nginx 10초 > WAS 5초. WAS 가 먼저 포기해도 nginx 는 계속 처리해 캐시를 채우므로, 같은 이미지의 다음 요청은 HIT 이 됩니다. nginx 가 먼저 포기하면 캐시가 영원히 안 채워집니다.

결과

배포 후 첫 영업일, APM 에서 30초 밴드가 사라졌습니다. 변환 서버의 같은 시간대 비교는 이렇습니다.

  • run queue: 22 → 0
  • 1분 load: 37.00 → 0.39~3.84
  • iowait: 13.4% → 0.1%
  • 캐시 엔트리: 142,504개 → 21.7시간 뒤 501,772개(3.5배). 시간당 증가량이 약 3개 → 수천~수만 개로 바뀌었습니다. 키 인덱스가 진짜 상한이었다는 확증입니다.

흥미로운 점은 하루 전체 최대 load 는 10.34 → 9.37 로 거의 그대로였다는 것입니다. 같은 시간대로 잘라서 비교해야 효과가 보였습니다.

남은 것

  • 변환 서버가 인스턴스 1대입니다. 통째로 죽으면 30초 대기가 다시 나타나므로, WAS 의 5초 패치는 이제 긴급 수정이 아니라 안전장치 역할입니다.
  • 5초가 적정한지 판단할 지연 분포(p95, p99)가 아직 없습니다.
  • APM 경보 임계값이 80초여서, 30초짜리 문제는 몇 주 동안 아무도 몰랐습니다.

배운 점

  • SQL 시간은 작고 외부 호출이 elapsed 를 지배하면, 조사 대상을 호출받는 쪽으로 옮깁니다.
  • 설정 주석의 가정을 실측합니다. 상한이 두 개(키 개수, 디스크 용량)면 어느 쪽이 먼저 걸리는지 계산합니다. “엔트리 수가 하루 수십 개만 늘고 정체”는 키 상한에 걸린 전형적인 신호입니다.
  • 횟수를 줄이는 것이 단가를 깎는 것보다 먼저입니다. 233배 차이가 우선순위를 정해 줬습니다.
  • 타임아웃은 혼자 정할 수 없습니다. 위아래 계층과 순서를 맞춰야 하고, 상대의 정상 응답시간과 상위 계층의 예산으로 정합니다.
  • 병목이 아닌 축을 최적화하지 않습니다. 스레드가 병목이라고 믿었다면 3초를 골랐을 것입니다.
  • 비교는 같은 시간대끼리. 하루 최대값은 아무것도 말해 주지 않았습니다.
  • 제가 틀린 것도 남깁니다. 14일 누적 로그 1,400건을 빈도로 잘못 읽었고(실제로는 시간당 4~5건), 바이트 단위를 MB 로 읽었습니다. 집계 전에 기간과 단위부터 확인합니다.
